Introduction to OOP and the course roadmap

Object-Oriented Programming (OOP) is a way of organising a program around objects. Each object bundles data with the operations that work on that data. Java is built around this idea, and almost everything you write in Java lives inside a class.

The video defines OOP as a programming paradigm that uses classes and objects to model real-world entities. The payoff is code reusability, modularity and easier maintenance.

Course roadmap

The series moves through these topics in order:

  1. Classes, objects and constructors (this part)
  2. Inheritance
  3. Polymorphism
  4. Encapsulation
  5. Abstraction
  6. Exception handling
  7. Collections framework
  8. File handling

The four pillars of OOP are encapsulation, abstraction, inheritance and polymorphism. The later parts cover them in depth. Everything in Part 1 is the groundwork they stand on: you cannot inherit from, hide the data of, or override behavior of a class until you can write and instantiate one.

Reusability and modularity are concrete benefits. A Student class written once can be used in a grading program, a library system and a timetable, and a bug fixed in the class is fixed everywhere it is used.

Interviewers often open with "What is OOP?". A good short answer: a paradigm that models a program as objects, each combining state and behavior, built from classes, with encapsulation, abstraction, inheritance and polymorphism as its four pillars.

Why classes? The parallel arrays problem

Before classes, ask how you would store the data of five students: a roll number, a name and marks. With only the types Java gives you, the natural answer is one array per attribute. The repo file OOPS/Main.java shows exactly this and then the class based fix.

// Every Java program starts at `public static void main`. Run this class to run the program.
// Java comes from a typed, class-based world, so we first look at WHY classes exist:
// without them we need one parallel array per attribute.
public class Main {
    public static void main(String[] args) {
        // Storing 5 students WITHOUT a class: one array per attribute.
        // Index i across all arrays is "student i" - nothing in the code enforces that.
        int[] rollNumbers = new int[5];
        String[] names = new String[5];
        String[] marks = new String[5];
        // Problem: adding a new attribute means adding another array and keeping them in sync.
        // A class bundles the attributes into one blueprint (see Student below).
        Student s = new Student();
        s.name = "Aditya";
        s.rollNumber = 1;
        System.out.println(s.name + " has roll number " + s.rollNumber);
    }

    // A class is a blueprint, like a Car design that needs an engine and seats.
    // From one blueprint we create many objects (a Maruti, a Ferrari, a Porsche).
    // This is a static nested class so main can create it directly with `new Student()`.
    static class Student {
        String name;
        int rollNumber;
        float marks;
    }
}
Aditya has roll number 1

Without a class, each attribute needs its own array. Index i across all the arrays means "student i", but nothing in the code enforces that. Adding a new attribute means adding another array and keeping them all in sync. A class bundles the attributes into one blueprint, so a single Student object carries everything about one student. Think of a Car design: one blueprint, many cars (a Maruti, a Ferrari, a Porsche).

You can run this file yourself from the OOPS folder:

cd OOPS
java Main.java

Here is how the parallel array version goes wrong. If you sort names alphabetically, rollNumbers and marks no longer line up, and the program still compiles and runs. With an array of Student objects (Student[] students = new Student[5]) you sort or move whole students, so the attributes always travel together.

Details of this file worth knowing:

  • Every Java program starts at public static void main(String[] args). Running the class runs that method.
  • Student is declared as a static nested class inside Main. That lets main, which is static, write new Student() directly. A plain non-static inner class would need an enclosing Main object first.
  • The notes show class Student as a separate top-level class. That is equally valid: a file may contain several classes as long as at most one is public and that one matches the file name. The nested form is used here only so the whole demo fits in one file.
  • The array marks in main is a String[], while Student.marks is a float. The parallel array version cannot even keep types consistent for you, which is another argument for the class.
  • java Main.java uses the single-file source launcher (Java 11+). It compiles in memory and runs the first class in the file, so no separate javac step is needed.

A class does not remove the need to initialise things. After new Student(), name is null and rollNumber is 0 until you set them. Constructors (later in this part) are the clean way to set those values at creation time.

Class: the blueprint

A class is a template that describes what its objects will look like and what they can do. It defines properties (instance variables, also called fields or attributes) and behaviors (methods). A class by itself holds no student data. It only describes the shape of a student.

A class is a blueprint or template used to create objects. It defines properties (instance variables/attributes) and behaviors (methods/functions). The example in the video is a custom student data structure. Instead of keeping separate variables for every student, a Student class is defined:

class Student {
    int rollNo;
    String name;
    float marks;
}

This class has three fields and no methods yet. Adding a behavior is just writing a method inside the class body:

class Student {
    int rollNo;
    String name;
    float marks;

    void greet() {
        System.out.println("Hi, I am " + name);
    }
}

A class is also a new type. Once Student exists you can declare variables of type Student, make arrays of it (Student[]), use it as a method parameter or return type, and put it in collections. This is how Java lets you build your own data types beyond int, double and String.

Naming convention: class names use PascalCase (Student, BankAccount), fields and methods use camelCase (rollNo, printDetails), and constants use UPPER_SNAKE_CASE (MAX_MARKS).

Object: state, behavior and identity

An object is an instance of a class: a real thing created from the blueprint that occupies memory. If Student is the blueprint, a particular student named Aditya with roll number 1 is an object.

An object is an instance of a class that occupies physical memory. It has three parts:

  1. State: represented by the attributes or properties (name, roll number, marks).
  2. Behavior: represented by methods (what the object can do).
  3. Identity: how the object is uniquely recognised in memory.

Creating and using objects

Use new to create an object, and the dot operator to reach its fields and methods. Each object gets its own copy of the instance fields.

Student a = new Student();
a.rollNo = 1;
a.name = "Aditya";

Student b = new Student();
b.rollNo = 2;
b.name = "Riya";   // changing b does not touch a

Identity versus equality

Two objects can hold exactly the same data and still be two different objects. Identity asks "are these the same object?" Equality asks "do these hold equal data?" For objects, == checks identity: it is true only when both references point to the very same object on the heap.

public class Main {
    static class Student {
        String name;
        Student(String name) { this.name = name; }
    }
    public static void main(String[] args) {
        Student s1 = new Student("Aditya");
        Student s2 = s1;
        s2.name = "Riya";
        System.out.println(s1.name);
        System.out.println(s1 == s2);
        Student s3 = new Student("Riya");
        System.out.println(s2 == s3);
        s1 = null;
        System.out.println(s1);
        System.out.println(s2.name);
        String a = "hi";
        String b = "hi";
        String c = new String("hi");
        System.out.println((a == b) + " " + (a == c) + " " + a.equals(c));
    }
}

s1 and s2 are one object, so changing the name through s2 shows up through s1. s3 holds the same name but is a different object, so s2 == s3 is false. Setting s1 = null only removes that reference; the object is still reachable through s2.

== on references compares identity. To compare contents you call equals, and for your own classes you must override it, otherwise Object.equals falls back to ==. The String class already overrides equals to compare characters, which is why a.equals(c) is true even though a == c is false (new String("hi") creates a separate object). a == b is true only because both literals share one pooled String object. Part 4 covers equals and hashCode fully.

Never compare strings with == in real code. It may appear to work for literals and then fail for strings built at runtime, such as input read from a user.

Typical question: "Difference between a class and an object?" A class is a compile-time blueprint that describes fields and methods. An object is a runtime instance created with new that holds actual values for those fields and takes up heap memory.

Stack vs heap memory

When a Java program runs, two regions of memory matter most for understanding objects: the stack and the heap.

Stack memory stores primitive data types, method frames and reference variables (pointers to objects). Heap memory dynamically allocates memory at runtime for the actual objects created with the new keyword.

Stack

Holds one frame per running method call. A frame has the method's local variables: primitives by value and references as addresses. When the method returns, its frame is removed instantly. Fast, small, automatic cleanup.

Heap

Holds every object and array, whatever method created it. It is shared by the whole program, much larger, and cleaned by the garbage collector rather than by method exit.

Two references to one object

Copying a reference copies the address, not the object. After Student t = s; there is still only one Student on the heap.

   t.rollNo = 9;   changes the one shared object, so s.rollNo is also 9.

A reference that points nowhere

A reference can hold null, which means "no object". Using a dot on a null reference throws NullPointerException.

   STACK                                 HEAP
   +--------------------+
   |  u   |  null       |   (points to nothing; no object exists for u)
   +--------------------+

   u.rollNo = 3;   // NullPointerException at runtime

Real JVMs refine this picture a little. Each thread has its own stack. A very small, short-lived object may be optimised by the JIT compiler (escape analysis) and never reach the heap at all. The mental model "locals on the stack, objects on the heap" is still the right one for reasoning about Java code.

A field that is a primitive (such as rollNo) lives inside its object, so it sits on the heap with that object. "Primitives live on the stack" is true for local variables and parameters, which is what the video means.

Declaring a variable creates no object. Student s; only makes a reference, and for a local it is not even initialised. Only new creates the object. Two common errors follow: calling methods on a reference that was never assigned, and assuming t = s gives you an independent copy.

Why primitives do not use new

Primitives such as int, char and boolean are stored directly on the stack for performance and speed, which avoids the overhead of heap allocation.

A primitive variable holds its value itself, so int age = 20; needs no object and no address. An object needs memory allocated on the heap, a constructor call and a reference, which costs more. For values as small and as heavily used as numbers, that overhead would slow every loop and every calculation, so Java keeps primitives as plain values.

The 8 primitive types are byte, short, int, long, float, double, char and boolean. Everything else, including String, arrays and your own classes, is a reference type. The price of using primitives is that they are not objects: they have no methods, cannot be null and cannot go into collections. Wrapper classes, covered below, solve that.

Interview question: "Where are objects and local variables stored?" Objects and arrays live on the heap. Local variables and method call frames live on the stack. A local reference variable lives on the stack, and the object it points to lives on the heap.

The new keyword

new dynamically allocates memory at runtime for an object and returns a reference to it.

The single line Student s = new Student(); hides several steps. Read it right to left.

  1. Declaration (left side): Student s creates a reference variable named s on the stack. It holds no object yet.
  2. Allocation: new reserves enough heap memory for all the fields of one Student and sets every field to its default value (0, 0.0, false, null).
  3. Initialisation: the constructor named after new runs on that fresh object and sets the real starting values.
  4. Reference returned: the new expression evaluates to the address of the new object.
  5. Assignment: that address is stored in s.
Student s = new Student("Aditya");

 1. Student s            STACK: s = (unset)
 2. new Student(...)     HEAP : [ rollNo=0, name=null, marks=0.0 ]   (defaults)
 3. constructor runs     HEAP : [ rollNo=0, name="Aditya", marks=0.0 ]
 4. address returned     value 0x4F2A
 5. s = 0x4F2A           STACK: s = 0x4F2A -----> the object

Each time new executes it creates a brand new object, even in a loop.

Student[] group = new Student[3];     // 3 null references, no Student objects yet
for (int i = 0; i < group.length; i++) {
    group[i] = new Student();         // now 3 separate objects
}

new Student[3] creates an array object whose three slots are null. It does not create three students. Reading group[0].name before filling the slots throws NullPointerException.

The word "dynamic" means the size and number of objects are decided while the program runs. A loop can create a thousand objects whose count was unknown at compile time, and the heap grows to hold them.

Objects passed to methods: the value of the reference

Java always passes arguments by value. For an object, the value that gets copied is the reference, not the object. The method receives its own copy of the address, which points to the same object as the caller's variable.

public class Main {
    static class Student {
        String name;
        Student(String name) { this.name = name; }
    }
    static void rename(Student s) { s.name = "Changed"; }
    static void replace(Student s) { s = new Student("New"); }
    static void bump(int n) { n++; }
    public static void main(String[] args) {
        Student st = new Student("Original");
        replace(st);
        System.out.println(st.name);
        rename(st);
        System.out.println(st.name);
        int k = 1;
        bump(k);
        System.out.println(k);
    }
}

  • rename follows the copied address to the shared object and changes a field, so the caller sees it.
  • bump receives a copy of the number, so k is unchanged.

"Java passes objects by reference" is a common wrong answer. Java has no pass by reference. A method can change the state of an object you hand it, but it can never make your variable point somewhere else.

Constructors: default and parameterized

A constructor is a special method invoked automatically when an object is instantiated. It is used to initialise the object's properties. It has the same name as the class.

Rules of a constructor:

  • Its name is exactly the class name.
  • It has no return type, not even void.
  • It runs once per object, as part of new, and cannot be called later like a normal method.
  • It can have access modifiers (public, private, and so on) and any number of parameters.
  • Constructors are not inherited by subclasses. A subclass has to declare its own, and it calls the parent's with super(...) (Part 3).

Default constructor

The default constructor is provided automatically by Java if no explicit constructor is defined. It leaves fields at their default values (0 for numbers, null for objects).

This is why new Student() worked earlier in Main.java, even though Student had no constructor written in it. The compiler quietly added Student() { } with an empty body.

The default constructor exists only while you write no constructor at all. The moment you add any constructor, even a parameterized one, the compiler stops generating the no-argument one. A call such as new Student() then fails to compile, unless you write a no-argument constructor yourself.

public class Main {
    static class Student {
        String name;
        Student(String name) { this.name = name; }
    }
    public static void main(String[] args) {
        Student s = new Student();   // compile error
    }
}

Parameterized constructor

A parameterized constructor lets you pass custom values during object creation to initialise the fields directly. Example from the video:

Student(int roll, String name, float marks) {
    this.rollNo = roll;
    this.name = name;
    this.marks = marks;
}

Now an object is fully set up in one line, with no window where it exists half-initialised:

Student s = new Student(1, "Aditya", 91.5f);

Note the f in 91.5f. A literal like 91.5 is a double, and Java will not silently narrow a double to the float parameter, so new Student(1, "Aditya", 91.5) does not compile.

If you give a constructor a return type, for example void Student() { }, it silently becomes an ordinary method that happens to be named Student. It will not run on new, and the compiler still generates the default constructor. This is a classic trap in interviews.

Interview question: "Can a constructor be final, static or abstract?" No to all three. A constructor belongs to the object being built, is not inherited so it cannot be overridden, and must have a body.

The this keyword and shadowing

this is a reference variable that points to the current object, the one whose method or constructor is being invoked. It is used to resolve shadowing when a parameter has the same name as an instance variable.

Inside a constructor or instance method, a simple name is looked up in the nearest scope first. A parameter named name hides (shadows) the field named name. Writing this.name says "the field of this object", so the compiler can tell the two apart.

Student(int rollNo, String name, float marks) {
    this.rollNo = rollNo;   // field = parameter
    this.name = name;
    this.marks = marks;
}

What goes wrong without this

public class Main {
    static class Student {
        String name;
        int roll;

        Student(String name, int roll) {
            name = name;          // parameter assigned to itself
            this.roll = roll;
        }
    }

    public static void main(String[] args) {
        Student s = new Student("Aditya", 1);
        System.out.println(s.name + " " + s.roll);
    }
}
null 1

name = name; assigns the parameter to itself. The field name is never touched and keeps its default null. The program compiles and runs with no error, which makes this bug easy to miss.

Shadowing mistakes compile silently. Many IDEs warn "assignment to itself". Always write this.field = parameter when the names match.

What this can do:

  • Refer to a field of the current object: this.name.
  • Call another constructor of the same class: this(...), shown next.
  • Be passed along or returned: return this; allows chained calls such as builder.a().b().c().
  • It cannot be used in a static method, because a static method runs without any current object.

Inside a method this is really a hidden first argument. When you write a.greet() and b.greet(), the same method code runs, and this is a in the first call and b in the second. That is how one method serves every object of the class.

Constructor overloading and this(...) chaining

Constructor overloading

Constructor overloading means having multiple constructors with different parameter lists in the same class.

Each constructor offers a different way to build the object. The compiler picks one by looking at the number, types and order of the arguments at the new call.

Calling one constructor from another with this(...)

Constructor logic can be reused by invoking another constructor of the same class with this(...).

Chaining sends the shorter constructors to the fullest one, so the real initialisation code lives in a single place.

public class Main {
    static class Student {
        int rollNo;
        String name;
        float marks;

        Student() {
            this(0, "Unknown", 0f);
        }

        Student(int rollNo, String name) {
            this(rollNo, name, 0f);
        }

        Student(int rollNo, String name, float marks) {
            this.rollNo = rollNo;
            this.name = name;
            this.marks = marks;
        }

        void greet() {
            System.out.println("Hi, I am " + name + " (roll " + rollNo + "), marks " + marks);
        }
    }

    public static void main(String[] args) {
        Student a = new Student();
        Student b = new Student(2, "Riya");
        Student c = new Student(3, "Karan", 88.5f);
        a.greet();
        b.greet();
        c.greet();
    }
}
Hi, I am Unknown (roll 0), marks 0.0
Hi, I am Riya (roll 2), marks 0.0
Hi, I am Karan (roll 3), marks 88.5

Order of execution in a chain

When a constructor starts with this(...), the called constructor runs completely first, and then the rest of the calling constructor's body runs.

public class Main {
    static class Pen {
        String color;
        int size;

        Pen() {
            this("black");
            System.out.println("Pen()");
        }

        Pen(String color) {
            this(color, 5);
            System.out.println("Pen(color)");
        }

        Pen(String color, int size) {
            this.color = color;
            this.size = size;
            System.out.println("Pen(color, size)");
        }
    }

    public static void main(String[] args) {
        Pen p = new Pen();
        System.out.println(p.color + " " + p.size);
    }
}
Pen(color, size)
Pen(color)
Pen()
black 5

this(...) must be the first statement in the constructor. Putting any statement before it, such as a println, gives the error call to this must be first statement in constructor. For the same reason a constructor can contain at most one this(...) call, and it cannot call itself in a cycle (A() calls A(int) which calls A()), which is a compile error as well.

Overloading is resolved at compile time from the argument types. new Student(2, "Riya") selects the two-argument constructor, and new Student(3, "Karan", 88.5f) selects the three-argument one. Two constructors cannot have the same parameter types in the same order, even if the parameter names differ.

When a constructor has many parameters, many overloads become hard to read. Later parts show the Builder pattern as an alternative. For simple immutable data carriers, Java 16+ records generate the constructor, getters, equals and toString for you: record Student(int rollNo, String name, float marks) { }.

Interview question: "What is constructor chaining and why use it?" It is one constructor calling another with this(...) (same class) or super(...) (parent class). It avoids duplicating initialisation code and keeps one constructor as the single source of truth.

Wrapper classes

Wrapper classes wrap primitive data types into objects, for example Integer for int, Float for float and Double for double.

All eight primitives have a matching wrapper class in java.lang:

Only int and char have names that differ noticeably from their wrapper (Integer, Character). The other six just capitalise the first letter. Wrapper objects are immutable: once created, an Integer never changes its value.

Why use wrapper classes

They let primitives be used in collections such as ArrayList, which accept only objects, and they provide utility methods.

  • Collections and generics need objects. ArrayList<int> does not compile, but ArrayList<Integer> does.
  • They can be null. An Integer can mean "no value", which a plain int cannot.
  • They carry useful methods and constants. Integer.parseInt("42"), Integer.MAX_VALUE, Character.isDigit('7'), Double.parseDouble("2.5"), Integer.valueOf("7").

Autoboxing and unboxing

Autoboxing and unboxing are the automatic conversions between a primitive and its wrapper class, done by the Java compiler.

  • Autoboxing: primitive to wrapper, such as int to Integer.
  • Unboxing: wrapper to primitive, such as Integer to int.
import java.util.ArrayList;
import java.util.List;

Pitfall: the Integer cache and ==

Integer.valueOf reuses cached objects for values from -128 to 127. Boxing a value inside that range gives you the same shared object each time. Outside the range, each boxing creates a new object. So ==, which compares identity, behaves differently for small and large values.

Never compare wrapper objects with ==. It happens to work for -128..127 and breaks above that. Use .equals(), or unbox one side so the comparison is between primitives (c == 200 with an int on one side compares values).

Pitfall: unboxing null

Unboxing calls a method on the wrapper object, so a null wrapper fails.

This hides in places that look innocent: int total = map.get(key); throws when the key is missing, because get returns null and the unboxing to int fails. Boxing in hot loops is also slower and creates garbage, so use primitives for heavy arithmetic.

equals on wrappers also checks the type. Long big = 5L; big.equals(5) is false because the argument boxes to an Integer, while big.equals(5L) is true. Wrappers of different types are never equal.

Interview question: "What is autoboxing, and what can go wrong?" The compiler converts between primitives and wrappers automatically. Risks are NullPointerException when unboxing null, wrong results from == outside the -128..127 cache, and performance cost from many temporary wrapper objects.

The final keyword

final is used to restrict the user. On a variable it makes the variable a constant, so the value cannot be reassigned. For an object reference marked final, the internal properties can still change, but the reference cannot point to a new object.

A final primitive is a constant

final int MAX = 10;
MAX = 20;      // compile error: cannot assign a value to final variable MAX

By convention constants are written in UPPER_SNAKE_CASE. A final variable may be declared first and assigned exactly once later (a "blank final"), including inside a constructor for a final field.

A final reference: the arrow is fixed, the object is not

With an object, final locks the reference, meaning which object the variable points to. It does not lock the fields inside that object.

public class Main {

Garbage collection and finalize()

Garbage collection is automatic memory management in Java. The Garbage Collector destroys unreferenced objects in the heap to free up system memory.

In Java you create objects with new and never write the code that frees them. The JVM runs a garbage collector (GC) that finds objects the program can no longer reach and reclaims their memory. This removes a whole class of bugs found in manual memory management, such as freeing an object twice or forgetting to free it.

When does an object become eligible for GC?

An object is eligible when no live part of the program can reach it through any chain of references. The GC checks reachability starting from roots such as local variables on active stacks and static fields. An object that cannot be reached from those roots is garbage, even if other garbage objects still point to it.

  1. Nulling the only reference: s = null; when no other reference holds the object.
  2. Reassigning the reference: s = new Student(); orphans the previous object.
  3. Going out of scope: a local reference disappears when its method returns, so an object created and held only inside that method becomes eligible.
Student a = new Student();   // object 1, reachable through a
Student b = a;               // still object 1, now two references
a = null;                    // object 1 is still reachable through b
b = new Student();           // object 1 now has no references: eligible for GC

Because the GC uses reachability, two objects that point at each other but are unreachable from outside are both collected. Reference counting would leak them, but Java does not use reference counting.

Even if an object is eligible, you do not control when it is actually collected. The JVM collects when it needs memory. System.gc() and Runtime.getRuntime().gc() are only a request, and the JVM may ignore them. Do not write programs that depend on a GC running at a given moment.

Garbage collection does not stop memory leaks. If a long-lived structure, such as a static List or a cache, keeps references to objects you no longer need, those objects stay reachable and are never freed. A memory leak in Java means unwanted references, not forgotten free calls.

The finalize() method

finalize() was historically used to perform clean-up tasks before an object is destroyed by the garbage collector. The notes mention that it is deprecated or superseded in modern Java.

In older Java, a class could override protected void finalize(), and the GC would call it once, just before reclaiming the object. The idea was to release resources such as open files. It did not work well in practice.

public class Main {
    static class A {
        @Override
        protected void finalize() {              // do not write this in new code
            System.out.println("cleaning up");
        }
    }
    public static void main(String[] args) {
        new A();
    }
}

finalize() is deprecated since Java 9 and marked for removal since Java 18. The compiler warns: [removal] finalize() in Object has been deprecated and marked for removal. Reasons:

  • There is no guarantee when it runs, or that it ever runs at all.
  • It slows down collection and can keep objects alive longer.
  • It can resurrect an object by storing this somewhere, and exceptions thrown in it are silently ignored.
  • It has caused security problems and hard-to-find bugs.

What to use instead:

  • try-with-resources: for anything that needs closing (files, sockets, database connections), implement AutoCloseable and let Java call close() at a predictable moment.
  • java.lang.ref.Cleaner: a safer last-resort mechanism for native resources, available since Java 9.
public class Main {
    static class Res implements AutoCloseable {
        final String n;
        Res(String n) { this.n = n; System.out.println("open " + n); }
        @Override public void close() { System.out.println("close " + n); }
    }
    public static void main(String[] args) {
        try (Res r = new Res("db")) {
            System.out.println("using " + r.n);
        }
        System.out.println("done");
    }
}

close() runs as soon as the try block ends, whether it ends normally or through an exception. A later part covers exception handling in more detail.

Interview question: "What is finalize() and should you use it?" It was a hook the GC called before reclaiming an object. It is deprecated for removal because it is unpredictable and unsafe. Use try-with-resources for deterministic cleanup and Cleaner only as a safety net.

Packages: what they are

A package is a named container that groups related classes, interfaces, enums and other packages. It does two jobs. It keeps a large code base organised, and it prevents naming conflicts, because the full name of a class is its package name plus its simple name. Two classes both called Date can live in the same program as long as they sit in different packages.

Packages are containers or folders used to group related classes, interfaces and sub-packages. They prevent naming conflicts and help organise large code bases.

How packages work

  • The directory structure of the project matches the package hierarchy.
  • The package keyword goes at the top of a file and declares which package the file's classes belong to.

The directory structure of your project matches the package hierarchy. package declares the package at the top of a file. import accesses classes from other packages.

The static keyword: an overview

Normally a field or method belongs to an object: you need an object before you can use it. A static member belongs to the class itself. It exists once per class, whether you create zero, one or a thousand objects.

static is a keyword used to manage memory efficiently. When a member is declared static, it belongs to the class rather than to any specific instance (object) of the class.

static can be applied to five things:

  • Variables (class variables).
  • Methods (class methods).
  • Initializer blocks (static { ... }).
  • Nested classes (static class Inner).
  • Imports (import static, seen above).

The memory saving is real but small. The bigger reason to use static is meaning: a value that is about the class as a whole (a counter of all students, a constant like Math.PI) should not be repeated inside every object. Top-level classes themselves cannot be static. Only nested ones can.

Static vs instance variables

An instance variable gets a fresh copy every time new creates an object, and each copy lives inside its own object on the heap. A static variable has a single copy for the whole class. Every object sees and changes that same copy.

A static method belongs to the class, so you call it through the class name. No object is needed.

Why main is static

public static void main(String[] args) { ... }

When you run java Main, no object of Main exists yet, and the JVM does not know which constructor to call or with what arguments. If main were an instance method, the JVM would need an object to call it on, but only code inside main could create that object. Making it static removes the problem: the JVM loads the class and calls Main.main(args) directly.

The JVM needs to call main before any object of the class is created. Making it static lets the JVM run it directly through the class name.

Each word in the signature has a reason:

  • public: the JVM is outside your class and must be able to see the method.
  • static: callable without an object.
  • void: the JVM does nothing with a return value. A program ends with System.exit(code) if it needs to report a status.
  • String[] args: command-line arguments, as in java Main one two.

Because main is static, the first thing most programs do is create an object and continue from there. Newer Java versions (preview in Java 21) relax the strict signature for beginners, but the classic form above is what every existing code base uses.

Writing static void main(String[] args) without public, or changing the parameter type, still compiles. The program just fails at launch with an error saying that main was not found. The compiler does not treat main as special.

Static blocks

A static block is a static { ... } section inside a class. It initialises static variables when a plain assignment is not enough. The JVM runs it exactly once, when the class is first loaded and initialised, which is before any object is created and before main runs if the block sits in the main class.

A static block is used to initialise static variables. It runs only once when the class is first loaded into memory, before any object is created.

Beyond the video: class loading and initialization order

The JVM loads a class lazily. It does not run a class's static initialisation at program start. It runs it the first time the class is actually used. "Used" means one of:

  • An object is created with new.
  • A static method is called.
  • A static field is read or written, unless it is a compile-time constant.

For one class, the order is:

  1. Static variable initialisers and static blocks, top to bottom, once.
  2. For each new: instance variable initialisers and instance initializer blocks, top to bottom.
  3. The constructor body.

Singleton class

A singleton class is designed so that only one object of it can ever exist in the program. It suits things that represent one shared resource: an application configuration, a logger, a connection pool manager.

Singleton is a design pattern that restricts the instantiation of a class to exactly one object.

The three steps

  1. Make the constructor private, so other classes cannot create instances with new.
  2. Create a private static instance of the class inside the class itself.
  3. Provide a public static method, usually called getInstance(), that returns that one instance.
public class Singleton {
    private static Singleton instance;

    private Singleton() {
        // Private constructor prevents outside instantiation
    }

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

    private static Lazy instance;

Without the sleep the race is rarer and harder to see, which makes it a worse bug, because it passes casual testing and fails in production. Making getInstance() synchronized in this program changes the output to objects created: 1. There are five standard fixes.

1. Eager initialization

class Eager {
    private static final Eager INSTANCE = new Eager();
    private Eager() { }
    public static Eager getInstance() { return INSTANCE; }
}

The JVM creates the object once during class initialisation, and class initialisation is thread-safe. Simple and safe. The downside is that the object exists even if nobody ever calls getInstance(), which matters if it is expensive to build.

2. Synchronized getInstance

class Synced {
    private static Synced instance;
    private Synced() { }
    public static synchronized Synced getInstance() {
        if (instance == null) {
            instance = new Synced();
        }
        return instance;
    }
}

Correct and lazy. The cost is that every call takes the lock, even long after the object exists.

3. Double-checked locking with volatile

class DoubleChecked {
    private static volatile DoubleChecked instance;
    private DoubleChecked() { }
    public static DoubleChecked getInstance() {
        if (instance == null) {                 // first check, no lock
            synchronized (DoubleChecked.class) {
                if (instance == null) {         // second check, with lock
                    instance = new DoubleChecked();
                }
            }
        }
        return instance;
    }
}

Only the first calls take the lock. volatile is required. Without it, the JVM may reorder the steps of new so that instance becomes non-null before the constructor has finished, and another thread could use a half-built object.

4. Initialization-on-demand holder idiom

class Holder {
    private Holder() { }

    private static class LazyHolder {
        static final Holder INSTANCE = new Holder();
    }

    public static Holder getInstance() { return LazyHolder.INSTANCE; }
}

The nested class LazyHolder is not initialised until getInstance() first touches it, which makes the singleton lazy. The JVM guarantees class initialisation runs once and safely, so no explicit locking is needed. This is a widely recommended choice for a lazy singleton.

5. Enum singleton

enum EnumSingleton {
    INSTANCE;
    public void doWork() { System.out.println("working"); }
}
// usage: EnumSingleton.INSTANCE.doWork();

The JVM guarantees exactly one instance per enum constant. It is thread-safe, short, and also safe against the reflection and serialization attacks below. Its limit is that an enum cannot extend another class (it can implement interfaces).

Reflection

A private constructor stops new, but reflection can switch off the access check:

c.setAccessible(true);

System.out.println(second == Eager.getInstance());

Two instances now exist. The same trick on an enum singleton fails: the JVM refuses to create enum objects reflectively (IllegalArgumentException: Cannot reflectively create enum objects). A class-based singleton can defend itself by throwing from the constructor if an instance already exists.

Serialization and class loaders

  • If a singleton class implements Serializable, deserialising its data creates a new object. A readResolve() method that returns the existing instance fixes this. Enums handle it automatically.
  • Cloning can duplicate an object, so a singleton should not implement Cloneable.
  • The guarantee is "one per class loader". Application servers with several class loaders can hold several copies.

When a singleton is a bad idea

  • Hidden global state. Any code can call getInstance() and change shared data, so behaviour depends on who ran before you.
  • Hard to test. A class that calls Config.getInstance() internally cannot be given a fake configuration in a unit test, and state leaks from one test into the next.
  • Hidden dependencies. The class's constructor does not show that it needs a Config.

The usual alternative is dependency injection (DI): create one object at start-up and pass it in through constructors. Frameworks such as Spring do this with singleton-scoped beans, so you get one shared object without a global getInstance(). The design-pattern chapters later in the series come back to this idea.

Do not turn every shared helper into a singleton. If a class has no state, plain static methods (like Math) are simpler. If it has state that tests need to change, inject it.

Inheritance: definition and benefits

Inheritance lets one class acquire the state and behaviour of another. The class that gives is the parent (also superclass or base class). The class that receives is the child (also subclass or derived class).

Inheritance is the mechanism by which a child class inherits the properties (variables) and methods (behaviours) of a parent class. The benefits are code reusability, extensibility and a relationship hierarchy between classes.

The keyword is extends:

class ChildClass extends ParentClass {
    // additional fields and methods
}
  • Reusability: write common code once in the parent, every child gets it.
  • Extensibility: a child adds new fields and methods, or changes inherited behaviour, without touching the parent.
  • Hierarchy: classes form a tree that models real relationships (Dog is an Animal).

Inheritance models an is-a relationship. A BoxWeight is a Box. A different relationship, has-a, means one class holds another as a field. A Car has an Engine, so Car should not extend Engine.

is-a (inheritance)

class Dog extends Animal. The child can be used anywhere the parent is expected. Tightly coupled to the parent's code.

has-a (composition)

class Car { private Engine engine; }. The class uses another object and forwards calls to it. Loosely coupled and easy to swap.

Interview: "When do you prefer composition over inheritance?" Short answer: use inheritance only when there is a genuine is-a relationship and the child honours everything the parent promises. In every other case hold the other object as a field. Composition avoids deep hierarchies, lets you change behaviour at runtime by swapping the field, and does not break when the parent changes its internals.

Every class you write already extends something. If you do not write extends, the compiler makes the class extend java.lang.Object. That is why every object has toString(), equals() and hashCode() without you writing them. A class can extend exactly one parent directly, so the full chain always ends at Object.

Java lets a class implement many interfaces instead. Interfaces historically had no state or method bodies, and where default methods clash, the compiler forces you to resolve the conflict.

Polymorphism: many forms

Polymorphism comes from Greek words meaning "many forms". In Java, one method name or one reference type can stand for several different behaviours or concrete types.

Polymorphism allows a single action or method to behave differently depending on the object or context calling it. Two types:

  • Compile-time (static) polymorphism: method overloading. The compiler picks the method from the signature (the arguments).
  • Run-time (dynamic) polymorphism: method overriding. A subclass provides its own implementation of a method already defined in the parent. The JVM picks the method at runtime based on the object type, not the reference type.

Signature rules

  • The signature is the method name plus the number, types and order of its parameters.
  • Overloads must differ in the parameter list: a different count, different types, or a different order of types.
  • The return type alone cannot distinguish overloads, and neither can parameter names or throws clauses.
  • Access modifiers do not matter for distinguishing overloads either.
int m(int a)  { return a; }

  1. Exact match or widening primitive conversion (int to long to double), or widening of references (subclass to superclass).
  2. Boxing or unboxing (int to Integer), then widening.
  3. Varargs (int...).

Run-time polymorphism: method overriding

Overriding means a child class supplies its own body for a method it inherited, using the same name and the same parameters. The parent's method stays available through super.method().

Dynamic method dispatch

When you write Parent obj = new Child();, the reference type is Parent and the object type is Child. If Child overrides a method, a call through obj runs the child's version. The JVM looks at the real object at the moment of the call. This is dynamic method dispatch.

Dynamic method dispatch resolves a call to an overridden method at runtime rather than compile time. The decision is made by the JVM from the object type, not the reference type.

This is why a Parent[] or List<Shape> can hold different children and each element does its own thing when you call the same method.

public class Main {
    public static void main(String[] args) {
        Parent p = new Child();
        System.out.println(p.me());          // object decides
        System.out.println(p.name);          // reference decides
        System.out.println(p.who());         // reference decides (static)
        System.out.println(Parent.who());
        System.out.println(Child.who());
        System.out.println(((Child) p).name);
        System.out.println(p.self().getClass().getSimpleName());

        Parent real = new Parent();
        System.out.println(real instanceof Child);
        System.out.println(p instanceof Child);
        System.out.println(p instanceof Parent);
        System.out.println(p instanceof Object);
        try {
            Child bad = (Child) real;
            System.out.println(bad);
        } catch (ClassCastException e) {
            System.out.println("ClassCastException");
        }
        if (p instanceof Child c) {
            System.out.println("pattern: " + c.extra());
        }
        Parent[] all = { new Parent(), new Child(), new Child() };

Only instance methods are polymorphic. Three things decide by the reference type instead:

  • Fields are not polymorphic. Parent p = new Child(); p.name prints Parent field. The child's name is a separate field that only hides the parent's one. Reach it with a cast: ((Child) p).name.

Upcasting and downcasting

  • Upcasting (child to parent) is automatic and always safe: Parent p = new Child();.
  • Through p you can call only what Parent declares. The compiler rejects p.extra(), even though the object has it.
  • Downcasting (parent to child) needs an explicit cast and is checked at runtime. If the object is not really that type you get ClassCastException.
  • Guard with instanceof before casting.

method hiding is the name for a child static method (or field) with the same signature or name as the parent's. Hiding is resolved from the reference type, overriding from the object type. That difference is the whole reason static and field lookups look "wrong" in the example above.

final with inheritance and polymorphism

Declaring a class final prevents it from being inherited. Declaring a method final prevents subclasses from overriding it.

final class

No subclass is allowed. String, Integer and the other wrapper classes are final. Use it to keep a class from being altered through subclassing, for example to guarantee immutability.

final method

Subclasses inherit it but cannot override it. Use it when a step must work exactly one way, for example a method that other methods in the class rely on.

public class Main {
    public static void main(String[] args) {
        Base b = new Derived();
        b.show();
        b.hello();
    }
}
class Base {
    final void show() { System.out.println("final show in Base"); }
    void hello() { System.out.println("hello from Base"); }
}
class Derived extends Base {
    @Override void hello() { System.out.println("hello from Derived"); }

Interview: "Can we override a final method? Can we overload it?" No to override, yes to overload. Overloading creates a different signature, so the final rule does not apply.

Encapsulation

Encapsulation is wrapping data (variables) and the code (methods) that acts on the data into a single unit, a class. It also means data hiding: restricting direct access to some components. It is achieved by declaring instance variables private and offering public getters and setters to view or change them safely. The analogy is a medicine capsule: the chemical contents are hidden inside a protective shell, and you use the capsule through defined guidelines.

Encapsulation brings real benefits.

  • Validation: the object cannot be left in an invalid state.
  • Flexibility: you can change how the data is stored (say, from double to BigDecimal) and callers do not notice.
  • Read-only or write-only fields: provide only a getter or only a setter.
  • Hooks: a setter can also log, notify or recompute.

Private fields with public getter and setter for every field is a bare minimum, and it can still break encapsulation. A setter with no validation is the same as a public field. A getter that returns a mutable object, such as a List or an array held in the field, hands the caller a way to change the hidden data. Return a copy or an unmodifiable view.

An immutability teaser: the strongest form of encapsulation is an object that cannot change after creation. Make the class final, make all fields private final, set them in the constructor and provide no setters. String works this way. Interview: "How do you achieve encapsulation in Java?" Make fields private, expose behaviour through public methods, validate in setters, and prefer to give out only what callers need. "Why are getters and setters better than public fields?" They let you validate, change the internal representation later, and keep the class in control of its own state.

Abstraction

Abstraction hides complex implementation details and shows only the essential features to the user. In Java it is achieved with abstract classes and interfaces. An abstract class cannot be instantiated directly. It can hold abstract methods (no body, subclasses must implement them) and ordinary concrete methods.

Think of a car. You use the steering wheel and pedals without knowing how the engine burns fuel. The interface you see is the abstraction. The engine is the hidden implementation.

public class Main {
    public static void main(String[] args) {

        d.draw();

Quick recap and common traps

  • A child gets the non-private members of its parent. Constructors are not inherited, but a child constructor must call one.
  • Constructors run parent first. If the parent lacks a no-argument constructor, call super(...) yourself as the first statement.
  • Classes allow single parent only. Interfaces give you multiple types.
  • Overloading is resolved by the compiler from declared argument types. Overriding is resolved by the JVM from the object.
  • Fields, static methods and private methods are never dispatched dynamically.
  • Override rules: same signature, same or covariant return, access not narrower, no broader checked exceptions, never static, private or final.
  • final class means no children, final method means no overriding.
  • Encapsulation is private fields plus controlled access. Abstraction is hiding implementation behind abstract types.
  • Downcast only after instanceof, or you risk ClassCastException.

Access control: the big picture

A class usually has a public face that other code may use and an inside that only it should touch. Java gives you four levels of visibility to draw that line. You put an access modifier in front of a field, a method, a constructor or a nested type, and the compiler refuses any use that the modifier forbids. The check happens at compile time, so a violation is a compile error and not a runtime surprise.

Access control is the set of rules Java uses to restrict where variables, methods and constructors can be accessed or modified inside a project. It protects data and keeps encapsulation intact. Java has four access modifiers: private, default (no keyword), protected and public.

The levels are ordered from tightest to widest: private, default, protected, public. Each step widens the set of code that can see the member. When unsure, start with the tightest level and widen only when another class really needs access. That keeps the surface other code depends on small.

There is no keyword default for access. Writing nothing is the default level. The word default in Java is used for switch and for interface methods, which is a different thing.

private

A private member can be used only inside the class body that declares it. Code in any other class, even a subclass or a class in the same package, gets a compile error. This is the strongest form of data hiding.

private members are accessible only within the declared class itself. They cannot be accessed from anywhere else, which gives strict data hiding.

public class A {
    private int priv = 1;

    void show() {
        System.out.println(priv);   // fine: same class
    }
}

A private constructor is a real technique. It blocks new from outside, which is how utility classes and singletons stop other code from creating instances. Private methods are helpers that you can change freely, because no other class can depend on them.

"Can a subclass see a private field of its parent?" The field still exists in every subclass object, but the subclass code cannot name it. It must go through a public or protected getter.

Default (package-private)

If you write no modifier, the member is visible to every class in the same package and invisible to every class in another package. It does not matter whether the other class is a subclass.

Default access (no modifier specified) means the member is accessible only within classes that live in the same package. It cannot be used from outside the package.

package a;

public class A {
    int pkg = 2;     // no modifier: package-private
}

Package-private is the right level for helpers that several classes of one package share but that are not part of the public API. A package is therefore a unit of encapsulation, not only a folder for tidiness.

a subclass in another package cannot see a package-private member of its parent. The compiler message says pkg is not public in A; cannot be accessed from outside package. That wording confuses people, because the member is not "public" and not "private" either. It means the member has default access.

protected

protected is the default level plus one extension: subclasses in other packages may also use the member, through inheritance. It is meant for members that a class wants to share with its children but hide from the rest of the world.

protected members are accessible within the same package and in subclasses (child classes) located in different packages, via inheritance.

package a;

public class A {
    protected int prot = 3;
}

"via inheritance" has a precise meaning. Outside the package, a subclass can use the protected member on this or on an object whose type is the subclass itself. It cannot use it on a plain reference of the parent type. The next topics show this with real compiler output.

"Difference between default and protected?" Both allow the same package. Only protected also allows subclasses in other packages.

public

public members can be used from any class in any package. Whatever you mark public becomes part of the contract of your class, so other code may depend on it and you cannot change it freely later.

public members are accessible from anywhere across all packages and classes.

package a;

public class A {
    public int pub = 4;
}

a public field gives up control of the value. Anyone can set it to anything. For data, prefer a private field with public getter and setter methods (see the getters and setters topic). Public is the normal choice for methods that form the class's API and for the class itself.

Getters and setters

A private field cannot be reached with obj.num from another class. To let outside code read or change it in a controlled way, the class exposes public methods that read it (a getter, getNum()) and change it (a setter, setNum()).

hashCode()

hashCode() returns an int that summarises the object. For a plain object with no override, the JVM derives it from the object's identity, so two different objects almost always get different numbers. It is often described as "the memory address as a number", but that is only an approximation of how the default value behaves.

hashCode() returns an integer (hash value) generated by an internal algorithm to represent the object's identity in memory.

The integer is not guaranteed to be unique. Two different objects can share a hash code (a collision), and the number is not the real memory address. The JVM may move objects during garbage collection, and the hash code stays the same. Hash-based collections use the number to pick a bucket quickly: HashMap and HashSet call hashCode() first and equals() second.

String, Integer, List and record classes override hashCode() to depend on their content. Their hash code is therefore the same for equal values on every run. The default Object version is the one that varies from run to run.

"Is hashCode() unique?" No. It is consistent for an unchanged object and equal for equal objects (when equals is overridden properly), but different objects may collide.

equals(): reference versus content

Two different questions can be asked of two references: "do they point to the same object?" and "do the objects hold the same data?". The operator == asks the first question. The method equals() is meant to ask the second, but the version inherited from Object only repeats the first.

equals() compares two objects. By default, == and equals() in the base Object class both check reference equality: whether both reference variables point to the exact same object in memory. Developers often override equals() to check content equality instead.

Overriding equals()

A good equals checks, in order: same reference (fast path), null, same class, then the fields.

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    Point p = (Point) o;
    return x == p.x && y == p.y;
}

the parameter type must be Object. Writing public boolean equals(Point p) is an overload, not an override. a.equals(b) may seem to work, but collections call equals(Object) and never see your method. @Override catches this mistake at compile time.

The rules equals must follow: it is reflexive (x.equals(x)), symmetric (x.equals(y) equals y.equals(x)), transitive, consistent across repeated calls, and x.equals(null) is always false.

"== vs equals?" == compares references for objects (and values for primitives). equals() compares whatever the class defines, and by default that is the reference. String, Integer and the wrapper classes override it to compare content.

The equals and hashCode contract

The video's follow-up note mentions that equals() and hashCode() must be overridden together. The reason is a rule in the Object documentation: if two objects are equal according to equals, they MUST return the same hashCode. The reverse is not required: two unequal objects may share a hash code.

The notes end by pointing out that equals() and hashCode() must be overridden together in custom classes.

The bug: equals without hashCode

A hash-based collection first finds the bucket from hashCode(), and only then calls equals() on the objects inside that bucket. If your class has a content-based equals but keeps the identity-based hashCode, two equal objects usually land in different buckets and the set never compares them.

The two checks make equals behave differently when a subclass is involved. The instanceof version treats a subclass object as equal to a parent object with the same data. The getClass() version treats them as different.

Abstract methods

Sometimes a parent class knows that every child must do something, but it has no sensible way to do it itself. A shape must have an area, an animal must make a sound, a payment must be processed. An abstract method records that requirement without supplying the code.

An abstract method is declared with the abstract keyword and has no body, meaning no {} implementation. It works as a mandatory template or contract: any child class that extends the abstract class must override it and provide an implementation for every abstract method.

abstract double area();          // ends with a semicolon, no braces
abstract void sound();

Think of an abstract method as a method signature only: return type, name, parameters, and optionally a throws clause. Callers can use it through a parent reference, and each child decides what actually runs.

Two things are compile errors. Giving an abstract method a body (abstract void f() { } gives "abstract methods cannot have a body"), and combining abstract with private (a private method cannot be overridden, so nobody could ever implement it).

An abstract method can have any access level except private: public, protected or package-private. An overriding method may widen access (protected to public) but never narrow it.

Abstract classes and the four rules

An abstract class is a class declared with the abstract keyword. It is a partly finished class: some methods are written, some are left as abstract methods for the children to complete.

If a class contains one or more abstract methods, the class itself must be declared abstract. The key rules from the video are:

  1. Cannot be instantiated. Parent p = new Parent(); is invalid, because the class has incomplete methods (methods without bodies) and calling them directly would lead to errors.
  2. Constructors. Abstract classes can have constructors. They are called through super() when a child class is instantiated.
  3. Static methods. Abstract methods cannot be static, because static methods belong to the class and cannot be overridden. Abstract classes can still contain regular static methods.
  4. Final classes. An abstract class cannot be final. final prevents inheritance, while an abstract class must be inherited and completed to be useful.

Three more facts complete the picture:

  • An abstract class can contain concrete methods and fields (instance and static, final and non-final). It does not have to contain any abstract method at all; abstract on the class alone just forbids new.
  • A class that has an abstract method (declared or inherited and not yet implemented) must itself be abstract, or the compiler rejects it.
  • A child class must implement all inherited abstract methods, or itself be declared abstract. The obligation then passes to the next child.

Constructors in abstract classes and call order

When you write new Dog(), the parent constructor runs first, then the child constructor. This holds when the parent is abstract. If you do not write super(...) yourself, the compiler inserts a call to the no-argument parent constructor. If the abstract class has only a parameterized constructor, the child must call it explicitly, as Circle did with super("Circle") above.

The order for new Circle(2) is: field initializers and constructor of Shape, then field initializers and constructor body of Circle. You can see it in the shapes output above, where "Shape constructor for Circle" prints before "Circle constructor".

Never call an abstract (overridable) method from an abstract class constructor. The child's fields are not initialized yet when the parent constructor runs, so the overriding method sees default values.

abstract class Base {

Why Java has no multiple inheritance with classes

Suppose a class C could extend both A and B, and both parents define show(). When someone calls c.show(), which one should run? This ambiguity is the diamond problem, named after the shape of the hierarchy.

        Animal
        /    \
     Bird    Horse        both override move()
        \    /
       Pegasus            which move() does Pegasus inherit?

Simplified:   A   B       both define show()
               \ /
                C         c.show() is ambiguous

If a class C were allowed to extend two parent classes (A and B) that both implement a method with the same signature, the compiler would not know which version to inherit. To avoid this ambiguity and keep code safe, Java does not support multiple inheritance with classes.

class A { void show() { System.out.println("A"); } }
class B { void show() { System.out.println("B"); } }
class C extends A, B { }
// error: '{' expected

The problem is worse than methods. Two parents also bring two copies of their fields and two constructor chains, and the language would need rules for initializing both. C++ solves this with virtual inheritance and extra syntax. Java chose to ban it for classes. A class still gets a chain of ancestors: C extends B extends A, and every class ends at Object.

Interfaces are the escape hatch. A class can implement many interfaces. Before Java 8, interfaces had no method bodies, so there was nothing ambiguous to inherit. Since Java 8, default methods bring the ambiguity back in one narrow form, and Java forces you to resolve it by hand (see the default methods topic).

. "Why no multiple inheritance in Java?" Short answer: to avoid the diamond problem, where a child inherits conflicting implementations (and state) from two parents. Java allows multiple inheritance of type through interfaces, which carry no instance state.

Interfaces

An interface is a pure contract: a list of capabilities that a class promises to provide. Where an abstract class says "I am a partly built Shape", an interface says "I can do Engine things".

An interface is a reference type in Java, similar to a class, used to achieve 100% abstraction and to support multiple inheritance. Before Java 8 it held abstract methods and constants (public static final variables). From Java 8 onwards it can also hold static and default methods.

Key characteristics:

  • No instantiation. Like abstract classes, you cannot create a direct object of an interface.
  • Variables declared in an interface are implicitly public, static and final (constants).
  • Methods are implicitly public and abstract by default.
  • Classes use the implements keyword to inherit from an interface.

Default methods

A default method is an interface method with a body, marked with the default keyword. Every implementing class gets it for free and may override it.

Default methods were introduced in Java 8 so that developers can add new methods to an interface, with a default implementation, without breaking existing classes that already implement that interface.

Why they exist. Before Java 8, adding a method to an interface broke every class that implemented it, since those classes suddenly lacked an implementation. The JDK itself needed to add methods like forEach to Iterable and stream() to Collection without breaking millions of existing classes. Default methods made that possible.

interface Greeter {
    void greet(String name);                       // abstract

    default void greetAll(String... names) {       // default: has a body
        for (String n : names) greet(n);
    }
}

A class implementing Greeter only needs greet. It inherits greetAll and can call it on its objects (a complete program is in the next topic).

When two interfaces have the same default method

If a class implements two interfaces that both define a default method with the same signature, the compiler cannot choose. This is the diamond problem returning in a small form. The class must override the method itself. Inside the override you can call a specific interface's version with InterfaceName.super.method().

interface Engine {
    default void start() { System.out.println("Engine start"); }
}

interface Brake {
    default void start() { System.out.println("Brake system check"); }
}

class Car implements Engine, Brake {
    @Override
    public void start() {              // mandatory: both defaults clash
        Engine.super.start();
        Brake.super.start();
        System.out.println("Car ready");
    }
}

public class Main {
    public static void main(String[] args) {
        new Car().start();
    }
}

The class wins over interfaces, a more specific interface wins over a less specific one, and a genuine clash forces the class to override and optionally delegate with X.super.m(). When to choose which

Choose an abstract class when

  • related classes share fields and common code
  • you want constructors or protected helpers
  • children are variations of one concept (Circle, Rectangle are Shapes)
  • you want to control how subclasses are initialized

Choose an interface when

  • unrelated classes should share a capability (Comparable, Runnable)
  • a class must have more than one such role
  • you only need a contract and callers should not care about the class
  • you want lambdas as implementations

A common design combines both: an interface defines the contract, and an abstract class implements part of it so that concrete classes only write what differs. The JDK does this with List and AbstractList.

interface Notifier {
    void send(String msg);
    void sendAll(String... msgs);
}

abstract class BaseNotifier implements Notifier {
    @Override
    public void sendAll(String... msgs) {      // implements one interface method
        for (String m : msgs) send(m);
    }
    // send() is left abstract: the subclass must supply it
}

class EmailNotifier extends BaseNotifier {
    @Override
    public void send(String msg) { System.out.println("Email: " + msg); }
}

public class Main {
    public static void main(String[] args) {
        Notifier n = new EmailNotifier();
        n.sendAll("a", "b");
    }
}

BaseNotifier implements sendAll and leaves send unimplemented. It does not need to repeat send in its body, because an abstract class may inherit an interface's abstract methods without implementing them.

On speed, the video says abstract classes are "slightly faster" and interfaces are "slightly slower due to interface lookups".

Do not choose on speed. There is a small truth behind the claim: on the JVM, calling a method through an interface (invokeinterface) needs a lookup that is a little more work than a class method call (invokevirtual). On modern JVMs, the JIT compiler caches the target at the call site and often inlines the call, so the measured difference is negligible in real programs. Design for clarity and flexibility instead, and measure only if a profiler points at a hot path.

. "Abstract class or interface?" A good short answer: use an interface to define a capability that unrelated classes can share, and an abstract class when related classes need shared state or code. Mention that since Java 8 the line is blurrier but state and constructors are still exclusive to abstract classes, and that a class can implement many interfaces but extend only one class.

Implementing an interface inline: anonymous classes, lambdas, functional interfaces

Writing a full named class for a one-off implementation is heavy. Java gives two shortcuts. Both are Beyond the video, but you will meet them constantly because interfaces are what they implement.

. An anonymous class declares and instantiates an implementation in one expression: new Discount() { ... }. A lambda is a short form that works when the interface has exactly one abstract method. Such an interface is called a functional interface. Adding @FunctionalInterface makes the compiler check that rule.

@FunctionalInterface
interface Discount {
    double apply(double price);        // exactly one abstract method
}

public class Main {
    public static void main(String[] args) {
        // 1. anonymous class
        Discount tenOff = new Discount() {
            @Override
            public double apply(double price) { return price * 0.9; }
        };

        // 2. lambda
        Discount flat50 = price -> price - 50;

        System.out.println(tenOff.apply(200));
        System.out.println(flat50.apply(200));

The interface type in the declaration is what gives the lambda its meaning: Discount flat50 = price -> price - 50; is legal only because Discount has a single abstract method taking one double.

Marker interfaces. An interface with no methods, such as java.io.Serializable, is used purely as a tag that the JVM or a library checks with instanceof.

An abstract class cannot be the target of a lambda, even if it has one abstract method. Lambdas work only with interfaces, which is one practical reason to prefer an interface for small contracts.

Annotations and @Override

An annotation is a tag written with @ that attaches information to a class, method, field, parameter or other element. It does not change what the code does by itself. Tools read it: the compiler, build tools, frameworks, or your own code at runtime.

Annotations (@Override, etc.) are metadata that provides data about the program to the compiler or runtime. For example, @Override ensures that a method is correctly overriding a superclass or interface method.

What @Override protects against

Without it, a typo in a method name or parameter list silently creates a new method instead of overriding the old one. With it, the compiler checks your intent.

class P { void f() { } }
class C extends P {
    @Override
    void g() { }       // error: method does not override or implement a method from a supertype
}
class Animal { void sound() { System.out.println("..."); } }
class Dog extends Animal {
    void Sound() { System.out.println("Woof"); }   // capital S: a new method, no warning
}
// Animal a = new Dog(); a.sound() prints "...", not "Woof".
// Adding @Override above Sound() turns the typo into a compile error.

It also catches a changed parent: if someone renames or removes f() in P, every @Override on a child now fails to compile, instead of silently becoming dead code. It works for implementing interface methods too, as the examples in this chapter show.

Built-in annotations:

  • @Override: this method overrides or implements one from a supertype.
  • @Deprecated: marks something as outdated. Callers get a compiler warning.
  • @FunctionalInterface: the interface must have exactly one abstract method.
  • @SuppressWarnings("unchecked"): silences a named compiler warning in that scope. Use it narrowly.
  • @SafeVarargs: declares that a generic varargs method is safe.

Custom annotations are declared with @interface. A retention policy says how long the tag lives: SOURCE (compiler only), CLASS (in the class file, the default) or RUNTIME (readable through reflection). @Target limits where it may be placed. Frameworks such as Spring and JUnit are built on this.

Nested interfaces

A nested interface is declared inside a class or inside another interface. It keeps a small contract next to the only code that uses it, and gives it a qualified name like Outer.Callback.

A nested interface is an interface declared inside another class or interface. It can be public, protected or private depending on where it is nested.

The access rules in detail.

Nested insideAllowed access
a classpublic, protected, private, or package-private (no keyword)
an interfacealways public (implicit). private or protected is an error

A nested interface is implicitly static. It does not belong to an instance of the outer class, so you never write outerObject.new Callback().

class Outer {
    interface Callback {               // nested interface (implicitly static)
        void done(String result);
    }

    private final Callback cb;

    Outer(Callback cb) { this.cb = cb; }

    void run() { cb.done("finished"); }
}

interface Shop {
    interface Item {                   // nested in an interface: implicitly public static
        String name();
    }
    Item first();
}

class Pen implements Shop.Item {
    public String name() { return "pen"; }
}

class Stationery implements Shop {
    public Item first() { return new Pen(); }
}

public class Main {
    public static void main(String[] args) {
        new Outer(r -> System.out.println("Got: " + r)).run();

        Outer.Callback c = new Outer.Callback() {
            public void done(String result) { System.out.println("Anon: " + result); }
        };
        c.done("ok");

        Shop.Item item = new Stationery().first();
        System.out.println(item.name());
    }
}

Program to an interface (and a sealed note)

The practical rule that ties this chapter together: declare variables, parameters and return types with the interface (or abstract class) type, and choose the concrete class in one place only. Code that depends on PricingStrategy does not need changing when a new strategy arrives.

interface PricingStrategy {
    double price(double base);
}

class Checkout {
    private final PricingStrategy strategy;   // depends on the interface only

    Checkout(PricingStrategy strategy) {      // injected from outside
        this.strategy = strategy;
    }

    double total(double base) {
        return strategy.price(base);
    }
}

public class Main {
    public static void main(String[] args) {
        PricingStrategy regular = base -> base;
        PricingStrategy festival = base -> base * 0.8;

        System.out.println(new Checkout(regular).total(1000));
        System.out.println(new Checkout(festival).total(1000));
    }
}

Sealed types (Java 17+). A sealed interface or class lists exactly which types may implement or extend it, so the set of implementations is closed and a switch over it needs no default branch. Verified on Java 21.

sealed interface Payment permits Card, Upi { }
record Card(String number) implements Payment { }
record Upi(String id) implements Payment { }

public class Main {
    static String describe(Payment p) {
        return switch (p) {
            case Card c -> "card ending " + c.number().substring(c.number().length() - 4);
            case Upi u -> "upi " + u.id();
        };
    }

    public static void main(String[] args) {
        System.out.println(describe(new Card("1234567890123456")));
        System.out.println(describe(new Upi("a@bank")));
    }
}
